# Results summary

All numbers are measured, not estimated. Reproduce with the commands in the README.

Sections 2–4 describe model **v1**. Section 5 describes model **v2**, trained after
the live tests found a gap in v1. Section 6 repeats everything on a second car,
**CAN-MIRGU**: the MIRGU model is the one now running on the chip (the ROAD
firmware is restored with `python ml/src/export_c.py` + `bash firmware/build.sh`).

## 1. CICIoV2024: why it cannot evaluate an AI detector

| | |
|---|---|
| Rows | 1,408,219, only **3,588 unique** (ID + 8 bytes + class) |
| Unique attack frames | DoS 21, gas 2, RPM 10, speed 5, steering 3 |
| Attack IDs seen in normal traffic | **none** |
| One-line rule "ID never seen in normal traffic" | **184,482 / 184,482 attacks, 0 false alarms** |

Published ~99.9% scores on this dataset come from duplicate rows and attack IDs
that never occur in normal traffic. It is used here for the **rules layer** only.
Details: `data_report.md`.

## 2. ROAD: the AI detector

Dataset: ORNL ROAD (Verma et al., PLoS ONE 2024), real vehicle, ~3 h of normal
traffic (24.1M frames, 106 IDs). Attacks forge frames on **legitimate IDs**;
masquerade versions remove the real frames so timing stays normal.
Details: `road_report.md`.

Split by whole recording: attack instance 3 → train, 2 → val, 1 → test;
the coolant attack exists once and is in **test only (never seen in training)**.
Threshold (0.98) and smoothing (5 of the last 10 frames of an ID) were chosen on
val and frozen before the single test run.

### Detector
1. **Rules**: ID whitelist, per-ID rate check.
2. **AI**: MLP 27 → 32 → 16 → 1, **1,441 parameters**, full int8,
   **5,232-byte** TFLite model. float and int8 decisions agree on 100% of val frames.
   Features: value never seen / outside normal range (per ID and byte), broken
   signal pairs (automatically found, e.g. gear ↔ reverse light), byte change since
   the previous frame of the ID, time since that frame. No raw byte values.
3. **Severity**: ALERT = unknown ID, wrong timing, or the model backed by strong
   evidence (impossible value or broken signal pair). WARNING = the model fired with
   only a never-seen value as evidence (possibly a new, normal car state).

### Rules only vs rules + AI (val)
| | Masquerade frames caught |
|---|---|
| Rules only | 0% |
| Rules + AI | 99.8–99.9% (every attack type) |

### Test set (int8 model, run once)
| Attack | Fabrication | Masquerade |
|---|---|---|
| Max speedometer | 99.8% | 99.8% |
| Correlated signal (wheel speeds) | 99.8% | 99.8% |
| Reverse light on | 99.8% | 99.8% |
| Reverse light off | 99.4% | 99.4% |
| Fuzzing | 93.9% | — |
| Max coolant temp (**never seen in training**) | 88.4% | **0% (missed)** |

All frames, all attacks: **99.2%** caught at ALERT level. Median delay to the first
alert ≈ 40 ms (5 frames at a 10 ms period); 406 ms for coolant (100 ms period).

| Clean test drives (22.9 min, never used for training or tuning) | Events | Frames/min |
|---|---:|---:|
| ALERT | 1 (2.6 per hour), in the "benign anomaly" drive | 0.26 |
| WARNING | 246, in the "benign anomaly" and "diagnostics" drives | 51.3 |

An event = flagged frames less than 1 s apart.

### Limitations (honest reading)
- **Coolant masquerade is missed.** Its byte varies too much between normal drives
  for the never-seen check, it has no signal partner, and its timing is unchanged.
  Nothing in the features can reveal it. The fabrication version is caught by timing.
- **WARNINGs are frequent on unusual drives** (deliberate benign anomalies,
  diagnostic sessions): the car shows values the training drives never contained.
  They are reported as "unknown state", not as attacks; a longer normal-traffic
  recording of the target car would reduce them.
- One recording per attack type in val and test: per-attack numbers rest on one
  capture each.
- The 0.5 ALERT-frames/min target used to pick the threshold was not reachable on
  val (3.2 at every threshold, one event); the highest threshold (0.98) was used.

Files: `road_mlp_int8_test.json`, `road_mlp_int8_val.json`, `road_mlp_config.json`,
`road_mlp_final_log.txt`, `road_profile.json` (the tables that go into the firmware).

## 3. On the STM32 (Nucleo-F446RE, Cortex-M4F at 180 MHz)

The whole detector (rules, 27 features, int8 MLP, smoothing, severity) is plain C
in `firmware/can_ids_fw/Core/Src/ids_detector.c`, with its tables and weights
generated by `ml/src/export_c.py`. No TFLite runtime on the chip: the 3-layer
int8 network is hand-written using the same arithmetic as TFLite, and two
multiply-adds per instruction (Cortex-M4 `SMLAD`).

### Same answers as Python, bit for bit
| Check | Frames | Identical model inputs | Identical int8 output | Identical ALERT/WARNING |
|---|---:|---:|---:|---:|
| C on PC vs Python, val split | 2,726,553 | 100% | 100% | 100% |
| C on PC vs Python, test split | 4,117,443 | 100% | 100% | 100% |
| **C on the STM32** vs Python (self-test at boot, real ROAD frames) | 3,600 | — | **100%** | **100%** |

The test split, re-scored with the C detector's own answers (same detector, no
tuning), gives exactly the published numbers above (99.23% at ALERT, 1 ALERT event,
246 WARNING events). Files: `c_detector_check.txt`, `stm32_selftest.txt`.

Timestamps: the chip uses integer microseconds. The candump logs store epoch
times (~1.1×10⁹ s) that Python parsed into float64, which adds up to ~0.2 µs of
rounding noise per gap; the comparison feeds Python the same exact microseconds.

### Cost on the chip
| | |
|---|---|
| Time per frame (rules + features + int8 MLP), measured with the DWT cycle counter | **63 µs** (11,361 cycles; max 11,684) |
| of which the int8 MLP | 49 µs (8,849 cycles) |
| CPU load at ROAD's ~2,400 frames/s | ~15% |
| CPU load on a 100% loaded 500 kbit/s bus (~4,000 frames/s) | ~25% |
| Flash (tables + weights + code) | 40.6 KB of 512 KB |
| RAM (per-ID history + int16 weights) | 5.1 KB of 128 KB |

The first, straightforward version (one multiply-add per loop pass, int8 weights
read from flash) took 115 µs per frame; widening the weights to int16 in RAM and
using `SMLAD` brought it to 63 µs.

## 4. Live on a real CAN bus

Setup: PC → THRYCY USB-CAN adapter (Robotell protocol, 1 Mbaud serial) → CAN bus at
500 kbit/s (SN65HVD230 transceiver) → Nucleo-F446RE running the detector on every
frame → JSON incidents on the ST-LINK serial port → PC. The PC replays each ROAD
recording at its original timing (`python pc/live_demo.py --all-test`): 99% of
frames left the PC within 0.05 ms of their recorded time.

**The whole test split was replayed: 4,117,443 frames in 31 minutes.**

| Recording (test split) | Detected live (ALERT) | Delay at the PC | Described by the Nucleo + signal table as |
|---|---|---:|---|
| Correlated signal, fabrication / masquerade | yes / yes | 118 / 125 ms | forged wheel speeds, value never seen |
| Fuzzing | yes | 66 ms | unknown CAN ID |
| Max coolant temp, fabrication | yes | 499 ms | 0x4E7 arriving faster than normal |
| Max coolant temp, masquerade (never seen in training) | **no** | — | — (missed offline too) |
| Max speedometer, fabrication / masquerade | yes / yes | 64 / 60 ms | forged speedometer, value never seen |
| Reverse light off, fabrication / masquerade | yes / yes | 43 / 136 ms | forged reverse light, contradicts the gear signal |
| Reverse light on, fabrication / masquerade | yes / yes | 94 / 75 ms | forged reverse light, contradicts the gear signal |

- **10 of 11 attacks detected**, the same ones as offline, and no false incident
  in the normal traffic of any attack recording.
- **Clean test drives (22.9 min):** 1 ALERT incident (the same one as offline, in the
  "benign anomaly" drive) and 233 WARNING incidents (offline: 246 events; an incident
  here merges WARNING and ALERT frames less than 1 s apart).
- **Nucleo under real traffic:** up to 2,580 frames/s, detector CPU at most 15.9%,
  receive queue at most 11 of 256 frames, **0 frames lost, 0 CAN errors**.

**Delay.** Median 75 ms (43–136 ms) from the PC sending the first forged frame to
the PC receiving the ALERT; 499 ms for coolant (100 ms period). It is the
detector's own delay (5 flagged frames ≈ 40 ms at a 10 ms period, as offline) plus
transport through the two USB links. Measured alone (unknown-ID frames, alerted
without smoothing): ~100 ms for a lone frame, median 30 ms (5–118 ms) inside a
continuous stream. The adapter buffers its serial input and flushes on an idle
timeout. In a vehicle the Nucleo sits directly on the bus and this transport delay
does not exist.

Files: `live_replay_test_v1.json`, `live_replay_log_v1.txt` (the PC console output: every
Nucleo report in readable form), `live_latency.txt`.

### Attacks that ROAD does not contain (generated live)

`python pc/live_attacks.py --all`: the PC plays the car (14 s of the clean test
drive `ambient_dyno_drive_basic_short`, no alert when replayed alone) and the
attacker (seconds 5–8). Fixed random seed; the detector is unchanged.

| Attack | Detected live (ALERT) | Delay at the PC | Bus load | Detector CPU | Frames lost |
|---|---|---:|---:|---:|---:|
| **DoS**, flood of unknown ID 0x000 (3 s) | yes, unknown-ID rule | 101 ms | 3,801 frames/s (≈ full bus) | 15.2% | 0 |
| **DoS**, flood of the car's own top-priority ID 0x006 with its real data | yes, rate rule | 12 ms | 3,800 frames/s | **24.1%** | 0 |
| **Fuzzing on real IDs**: random data on random whitelisted IDs, 1 per ms, on top of normal traffic | yes, rate rule (0x522 first) | 104 ms | 3,393 frames/s | 21.6% | 0 |
| **Fuzzing masquerade**: one real ID (0x00E, 10 ms period, never attacked in ROAD) carries random data, timing unchanged | **no** (no ALERT, no WARNING) | — | 2,393 frames/s | 15.2% | 0 |

During a DoS the car's own frames cannot win arbitration against the flood, so
they are left out of the attack window. One USB-CAN adapter sends everything,
so real arbitration between two senders is not reproduced; what the Nucleo sees
(a full bus of flood frames) is.

- **The Nucleo keeps up with a full bus.** 3,800 frames/s through the whole
  detector (rules + features + MLP on every frame) used 24.1% CPU (predicted 25%
  in section 3), queue at most 8 of 256, no frame lost, no CAN error.
- **Random data at normal timing is missed.** Python's reference detector gives
  the same answer as the chip on these frames: every forged 0x00E frame has most
  bytes at never-seen values (novelty count at its maximum), but the model's
  score stays near 0 on 90% of them, so 5 of 10 is never reached. The MLP learned
  ROAD's attacks, where one or two bytes of an otherwise real frame are changed;
  a frame where everything is new does not look like them. This is a limit of
  learning from a few attack types; a plain rule ("several bytes never seen at
  once") would catch it, but it is not part of the evaluated detector.
- **ALERTs continue after a flood on a slow ID.** The 5-of-10 history counts
  frames, not time: 0x006 is sent once per second, so after the flood its next
  normal frames are still reported as ALERT until 6 normal frames have arrived
  (3 short ALERT incidents in the 6 s after the attack, counted as false by the
  script). Fuzzing on real IDs shows the same tail on its slow IDs.

Files: `live_attacks_v1.json`, `live_attacks_log_v1.txt`.

## 5. Model v2: random data on real IDs (post-test revision)

**Why.** The live test `fuzz_masquerade` (section 4) showed that v1 misses a real
ID carrying random data at its normal timing. v1 only learned ROAD's attacks, where
one or two bytes of an otherwise real frame change. **This revision was made after
the test split had been used**, and is reported as such, next to v1.

**What changed.** Only the training data and the weights. Same 27 features, same
27 → 32 → 16 → 1 network (1,441 parameters, 5,232-byte int8 model), same C code,
same rules and severity. Training also gets synthetic attacks
(`ml/src/synthetic_attacks.py`): 20 s pieces of normal drives with one attack on one
ID: all 8 bytes random / 3–5 random bytes (masquerade) / extra frames with 3–8
random bytes (fabrication). Nothing is shared between splits: training attacks use
training drives and 70% of the IDs; val and test attacks use their own drives and
their own 15% of the IDs each. **0x00E (the live test) is a test ID, never attacked
in training.**

**How it was decided, in order (nothing hidden):**
1. On val, a first version with 2–4 random bytes raised the WARNINGs on the clean
   val drive from 23.5 to 147 frames/min: normal driving has frames with 1–2 new
   values (1,902 of 1.72M) but almost never 3+ (4). Changed to 3+ random bytes.
2. v2 was evaluated on test with an extra severity rule "3+ never-seen bytes in one
   frame = ALERT", calibrated on val. **It failed: 36 false ALERT incidents on the
   clean test drives (v1: 1).** The "benign anomaly" drive has 1,232 such frames;
   the 12.5 min of val drives were too short to show how common they are.
3. The rule was removed **after** that test run (v2 = v1's severity rule). The final
   v2 numbers below are therefore **test-informed**: they need confirmation on data
   not used so far (planned: a second dataset, CAN-MIRGU).

### Test split (ROAD test attacks + 40 synthetic attacks on held-out IDs and drives)
| | v1 | v2 + 3-byte rule (failed) | **v2 (on the chip)** |
|---|---:|---:|---:|
| ROAD test attack frames at ALERT | 99.23% | 99.23% | **99.23%** |
| Random-data attacks detected (ALERT or WARNING) | 18 / 40 | 38 / 40 | **38 / 40** |
| … of which at ALERT | 11 / 40 | 28 / 40 | 17 / 40 |
| Random-data attack frames flagged (ALERT or WARNING) | 23.7% | 94.6% | **94.6%** |
| Clean test drives (22.9 min): ALERT incidents | 1 | **36** | **1** |
| Clean test drives: WARNING incidents | 246 | 149 | 95 |
| Clean test drives: WARNING frames/min | 51 | 418 | **472** |

Val (chosen there, before any test): random-data attacks detected 11/40 (v1) → 40/40
(v2); clean val drive: 1 ALERT incident for both, WARNING incidents 1 → 3.

**On the chip:** C vs Python on every val and test frame including the synthetic
attacks (10.5M frames): 100% identical inputs, outputs and levels
(`c_detector_check_v2.txt`); boot self-test 3,600/3,600, still 63 µs per frame
(`stm32_selftest_v2.txt`).

| | v1 live | **v2 live** |
|---|---:|---:|
| ROAD test attacks detected (ALERT) | 10 / 11 | **10 / 11** (same; coolant masquerade missed) |
| False incidents in the attack recordings | 0 | **0** |

Fewer WARNING incidents but longer ones: v2 warns continuously during long

v1 reported as 231 separate incidents now form one long incident. A WARNING LED
would stay lit through such a state. Files: `live_replay_test.json`, `live_replay_log.txt`.

### What v2 costs (honest reading)
- **More WARNING frames on unusual drives (×9 frames, fewer incidents).** Long harmless
  states with never-seen values (0x5E1 in "benign anomaly", 0x6FC in "basic short")
  look like random data to the model. They are reported as "unusual", not "attack".
  A never-seen harmless state and random data are close in these features; more
  normal driving of the target car is the real fix.
- **Random data is often only a WARNING** (21 of the 38 detected attacks): ALERT needs
  strong evidence (impossible value or broken signal pair), which random data does
  not always produce.
- **Test-informed:** see step 3 above.
- The synthetic attacks are our own design; held-out IDs and drives keep the test
  honest about *new IDs*, not about attack styles we did not think of.

Files: `road_mlp_v2_final_log.txt`, `road_mlp_v2_int8_test.json`,
`road_mlp_v2_config.json`, and the failed step 2: `road_mlp_v2_with_3byte_rule_*`.


## 6. Second car: CAN-MIRGU (independent check, and the live showcase)

CAN-MIRGU (Rajapaksha et al., VehicleSec 2024, CC BY 4.0): a 2016 electric car,
500 kbit/s, 56 CAN IDs. **16.0 h of normal driving** on UK public roads over 6 days
(May–June 2023; 55 silent minutes removed), and 36 attack recordings with per-frame
labels, made on a proving ground in October 2023. Data report: `results/mirgu/mirgu_report.md`.

**Same code, same network, same features** as ROAD (`IDS_DATASET=mirgu`), trained
like v2 (real attacks + synthetic random-data attacks).

**Split, fixed before any model ran** (`ml/src/mirgu_split.py`): Days 1–4 train,
Day 5 val, Day 6 test. Attacks split by type, copies kept together (real + masquerade,
min speedometer 1/2/3, gear shifter 1/2, both EMS replays); replays and suspensions
test only. Every val/test attack type is one the model never saw.

**Data handling found on the way** (no result looked at):
- 7 of the 12 normal files contain silences > 1 s (parked, up to 18 min). The chip
  forgets its history after 1 s of silence, so each file is cut there (20 captures);
  silent time does not count as driving.
- Suspension recordings label every frame of the window 1, but no frame is forged
  (an ID just stops): stored as label 0, scored separately (incidents in the window).
  They are 26 min cut out of the 4 May drive (Day 1), so their normal parts come from a training trip.

### Decisions, in order (nothing hidden)
1. **Val (allowed):** the ROAD severity rule never gave an ALERT on MIRGU: its
   "impossible value" check only ran on bytes whose novelty check is the range, and
   MIRGU's profile uses the exact set of seen values on 415 of 448 bytes. MIRGU now
   counts a byte beyond its range + margin as strong evidence on every checked byte
   (`common.RANGE_STRONG_ALL_CHECKED`, a `#define` on the chip). Model inputs are
   unchanged; on val, masquerade/random attacks went from WARNING to ALERT with the
   same 3 false ALERT incidents. ROAD keeps its rule (ROAD results unchanged, re-checked).
2. Test scored once (results kept in `results/mirgu/before_october_fix/`).
3. **Post-test revision.** The first live replay of a test recording raised an
   ALERT before the attack started. Cause: the normal days are May–June, all attack
   recordings are October, and some constant signals changed in between (0x507:
   `00 00 00 01` → `08 00 00 21`). Detection tables only scored forged frames and clean
   days, so the false alarms on the **normal frames inside attack recordings** were
   not counted: they are now (also on val, where the problem was already visible).
   Fix: the profile also learns the normal parts of the **training** attack recordings
   (> 5 s away from the attack). Test was re-scored; both versions are reported.

### What this shows (honest reading)
- **The method carries over to another car.** Same code, same 1,441-parameter
  network, retrained in 5 minutes. On a day it never saw, the MIRGU model gives
  **2.5 false WARNING incidents per hour** (ROAD v2 on ROAD: 249/h).
- **Training on the car matters.** ROAD's network with a MIRGU profile still detects
  the attacks, but flags normal new values all the time (788 WARNINGs/h): it learned
  ROAD's driving, where a new value is rarer.
- **Most real MIRGU attacks are caught by the rules alone** (90.8%): they inject
  frames on top of the real ones (rate rule) or use IDs not in the car (whitelist).
  MIRGU's "replays" also inject, so timing catches them; a pure replay that replaced
  the real frames would still be missed. The AI adds random/new-value attacks, the
  max speedometer (97% at WARNING), and the door attack on val (plausible values, too fast).
- **Missed:** the wiper masquerade (a half-byte set to a value the car really uses,
  on a 200 ms ID) and the suspensions (no "missing ID" rule), as expected.
- **False ALERTs:** 1.9/h on clean driving, all from the rate rule (slow IDs that
  sometimes arrive early). Inside the October attack recordings, 25 incidents in
  55 min remain after the fix, almost all from one ID (0x381, power steering) in the
  two "multiple attacks" recordings of the 26 October session: the context changed
  again. The fix also cost some ALERT recall on synthetic 3–5-byte attacks (97.0% → 88.6%).
- The fix is test-informed and the test attack recordings share their sessions with
  the training ones, so the attack-recording false alarms are optimistic; clean Day 6
  stays the independent measure.

  same October context shift seen offline (0x381 and 0x394 are where offline put its

- **The live scoring was corrected after this run.** At first, `live_demo.py` credited
  these 3 as detections with a *negative* delay. It now marks an ALERT raised before
  the first forged frame as a false alarm (`detected: "masked"`). The saved JSON was
  re-scored by hand from the log, and the run was not repeated.
- **Clean Day 6:** all 4 false ALERTs are in the two short pieces (20 s and 59 s of traffic
  between bus silences), in their first seconds: 0x410 arriving early when the bus
  wakes up, and 2 changes on 0x5BE. Offline, all of Day 6's false ALERTs fall in those

- **Chip load:** up to 2,021 frames/s, detector CPU at most **12.8%**, queue at most 14
  of 256 frames, **0 frames lost**, 0 CAN errors; 99% of frames were sent within 0.08 ms of
  their recorded time.
- **For the demo:** use the single-attack recordings that ran clean live (max_speedometer,

## 7. Device protection (step 3, in progress)

The detector itself has to survive attacks on the device: someone hanging it, glitching
its supply, reading its firmware out, or flashing a version without the detector.
Code: `firmware/can_ids_fw/Core/Src/ids_security.c`; tests: `python pc/security_demo.py <test>`,
log: `results/security_tests.txt`. At every boot the firmware prints one line with the reset
cause and the protection settings it reads from the option bytes:

```
{"type":"boot","reset":"watchdog","rdp":"level0","bor":"level3_2.70V","wrp_sectors":[],"watchdog":"software","watchdog_ms":250,"demo_commands":true,"secret":"present","secret_id":"fe096ce0","boot":3,"seq":0,"mac":"<32 hex digits>"}
```

| ID | Protection | Test | Result |
|---|---|---|---|
| L2 | **Independent watchdog** (IWDG, 250 ms, its own oscillator, cannot be stopped once started) | `security_demo.py watchdog`: the PC sends `H`, the firmware hangs on purpose (interrupts off, endless loop) | **PASS**: restarted **251 ms** after the hang, reset cause reported `watchdog` |
| L2b | Watchdog vs real load | DoS flood at 3,800 frames/s (`live_attacks.py dos_unknown_id`), MIRGU max_speedometer replay at ~2,000 frames/s | **PASS**: no watchdog reset, 0 frames lost |
| P2 | **Tamper switch** on PC13 (RTC tamper input; the Nucleo's blue USER button plays the enclosure switch): erases the device secret in hardware | `security_demo.py tamper`, button pressed by hand | **PASS**: backup registers read back as zero, LD2 on, detector kept running, still `erased` after a restart |
| P2b | **Device secret made on the chip**: ECDH P-256 with the provisioning PC; the chip's key pair comes from its own entropy source; only public keys cross the cable | `security_demo.py provision` | **PASS**: chip and PC derived the same secret (fingerprints match), 244 ms in all; a second provisioning is **refused**; an invalid PC public key is **refused**; 3 provisionings gave 3 different key pairs; the secret survived restarts, a watchdog reset and a reflash |
| E1 | **On-chip entropy source** (no hardware RNG on the F446): LSI RC-oscillator jitter measured by TIM5 against the crystal clock, 4,096 samples → health tests → SHA-256 | `pc/entropy_check.py` (32,768 raw samples per setting) | **~2.8 bits of min-entropy per sample** (most-common-value: 2.88, predictor from the previous sample: 2.82); one sample every 32 µs; ~11,500 bits estimated per 256-bit seed |
| N4 | **Signed serial link**: every JSON line carries `boot`, `seq` and an HMAC-SHA256 (128 bits) made with the device secret; the PC (`pc/signed_link.py`) checks it | `security_demo.py signing` | **PASS**: 6/6 real lines verified; one value changed → *forged*; made-up ALERT → *forged*; genuine line sent again → *replayed*; other key → *forged*. Live replay: 76/76 lines verified, detection unchanged. HMAC **220 µs** per line on the chip |
| P2c | Power loss vs tamper | USB unplugged 5 s, then `status` | **PASS**: reported `missing` (power lost), not `erased` |
| P3 | **Brown-out reset level 3** (option byte BOR_LEV): the chip is held in reset below 2.70 V instead of running at a voltage where flash reads and code can go wrong (simple supply glitches) | option bytes read back by the firmware at boot | **set**: `bor: level3_2.70V` (not tested with a real supply dip) |

- **Why 250 ms:** the IWDG runs on the internal LSI oscillator, which the datasheet only
  guarantees between 17 and 47 kHz, so 250 ms nominal can be as short as ~170 ms. The longest
  main-loop pass is a full 256-frame queue (256 × 63 µs = 16 ms) plus a few serial lines.
- **The demo command is a backdoor by design:** anyone on the USB serial port can hang the
  chip (and get it restarted). A production build sets `SEC_DEMO_COMMANDS 0`; the port then
  accepts nothing.
- A reset loses the detector's history (a few seconds to re-learn timing). `live_demo.py`
  now shows any restart during a run and records it in the results (`nucleo_resets`).

### Tamper and device secret: how it works, and what went wrong first
- The key stands in for what a real ECU keeps in tamper-protected memory (SecOC or
  diagnostic keys). The firmware never sends it out: it prints only a 32-bit fingerprint
  (FNV-1a), so the PC can check that provisioning worked.
- **The F446 has no hardware random generator** (only some F4 parts have one, such as the
  F405/F407/F427/F429), so the chip harvests its own randomness:
  - **Source:** the internal LSI RC oscillator (~31 kHz) drifts and jitters with thermal noise,
    and the 90 MHz timer clock comes from an independent crystal. TIM5 can capture the LSI
    directly (a hardware path meant for LSI calibration), so each sample is the length of one
    LSI period in 90 MHz ticks: mean 2,886 ticks, standard deviation ~3 ticks.
  - **Measurement** (`results/entropy_check.txt`, 32,768 samples per setting):
    | LSI periods per sample | 1 | 2 | 4 | 8 |
    |---|---:|---:|---:|---:|
    | min-entropy per sample, most common value (bits) | 2.88 | 3.64 | 4.57 | 5.33 |
    | min-entropy, guessing from the previous sample (bits) | 2.82 | 3.41 | 4.12 | 4.68 |
    | correlation with the previous sample | +0.39 | +0.58 | +0.74 | +0.83 |

    Consecutive samples are correlated (the oscillator also drifts slowly), so the plain
    estimator could overestimate. The second estimator guesses each sample from the one before
    it and still finds about the same entropy, so the correlation does not make samples
    predictable. Setting chosen: 1 period per sample (least correlated, fastest).
  - **Use:** 4,096 samples (0.13 s, ~11,500 bits by the estimate) are hashed into a 256-bit
    seed. This is still enough if the true entropy were 40 times lower than measured. Two
    health tests from NIST SP 800-90B (repetition count, adaptive proportion; cut-offs for
    2.8 bits/sample at a 2⁻³⁰ false-alarm rate) refuse to make a key from a stuck or biased
    source.
  - **Honest limit:** this is two estimators on 32,768 samples, not the full SP 800-90B
    assessment (ten estimators, 1,000,000 samples, restart tests), and it was measured on
    one board at room temperature.
- **ECDH provisioning (`"Q"` + the PC's public key):**
  - The chip checks that the PC's P-256 public key is a valid curve point, then makes its own
    key pair from the seed (micro-ecc, `Core/Src/uecc/`, BSD licence) and answers with its
    public key.
  - Both sides compute the same ECDH value and hash it with both public keys into the
    128-bit secret. Someone watching the cable sees only the two public keys and cannot
    compute it.
  - The chip's private key, the ECDH value and the seed are wiped right away. The PC throws
    its private key away and keeps only the derived secret, which it needs to check the HMACs.
  - The secret is written only into an empty slot: an attacker on the serial port cannot
    replace it. Only a tamper or a power loss empties the slot.
  - **Limit:** the ECDH is not authenticated. It defeats a *listener*, but someone who can
    replace the PC's public key with their own during provisioning gets the secret instead.
    The provisioning station must be trusted, as on a production line.
- A tamper event clears every backup register **in hardware**, within the filter time, even
  if the firmware is hung. The interrupt only reports it (JSON `"type":"tamper"`, LED) and
  marks the status line `"secret":"erased"`. Detection keeps running: losing the key must
  not switch off the IDS.
- **Erased vs missing:** at power-up the firmware writes a "blank" marker into a sixth backup
  register. A tamper clears it too, so `erased` means "tampered since the last power-up"
  and `missing` means "power was lost, not provisioned since".
- **Limit of the Nucleo:** VBAT is wired to the 3.3 V supply, so unplugging USB also clears
  the key, and nothing watches the switch while the board is off. A coin cell on VBAT
  (after opening the board's VBAT-to-VDD solder bridge, see the Nucleo user manual UM1724)
  would keep the backup domain, and the tamper detection,
  running with the board unpowered.
- **Finding during development:** the first version used *edge* detection without a filter.
  Turning it on erased the key by itself at every reset, with the button untouched. The
  registers held the key when the firmware started reading them and were zero a few
  microseconds later (read over SWD). The fix is *level* detection with a filter: the input
  must read low on 4 samples in a row (~32 ms with the LSI clock), with the pin precharged
  before each sample. This also resists short glitches on the line. The key then survived
  every restart.

### Signed serial link: what it protects, and what not
- **Threat:** the dashboard trusts what arrives on the USB serial link. Anyone with access to
  that link (or to the PC's serial port) could inject a fake ALERT, change one, or hide a
  real one by sending fake "all quiet" status lines. With the HMAC, a line that was changed
  or made up fails the check (`forged`), and a genuine line recorded earlier and sent again
  fails too (`replayed`: its `(boot, seq)` is not newer). `live_demo.py` ignores such lines
  and counts them.
- **The tamper link:** after a tamper the key is gone, so the Nucleo sends its lines with
  `"mac": null`. The PC can see that the device can no longer prove what it says.
- **How the line is signed:** the firmware rebuilds each `printf` line, then appends `"boot":B,"seq":N}`. It
  signs that text (HMAC-SHA256 with the 16-byte key, first 128 bits kept) and inserts `,"mac":"…"` before
  the closing brace. SHA-256 and HMAC are written in the project
  (`Core/Src/sha256.c`), checked on the PC against the FIPS 180-4 and RFC 4231 test vectors
  and against Python's `hashlib`/`hmac` on 3,000 random inputs (identical).
- **Limits:**
  - *Authenticity only:* the lines are still readable by anyone on the link (not encrypted).
  - *Hiding by silence:* an attacker who cuts the link can still hide alerts by silence.
    The dashboard should treat "no signed status line for 2 s" as an alarm.
  - *Replay after a PC restart:* the PC remembers the newest `(boot, seq)` only while it
    runs, so an old line replayed right after a PC restart is accepted once.
  - *The PC's copy of the key:* it sits in `keys/device_secret.key` (git-ignored, mode 600),
    so whoever controls the PC can sign lines too.

reflashed or debugged again) and is not applied.
